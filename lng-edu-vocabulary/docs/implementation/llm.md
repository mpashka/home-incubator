# Работа с языковыми моделями

Родительский индекс: [index.md](index.md)

Эта страница — владелец решения о выборе модели и устройства слоя работы с моделями.
Задачи, для которых модели используются, перечислены в [plan.md](../plan.md), этапы 9 и 10.

## Решение

**Начинаем с моделей Yandex.** У проекта есть квота в Yandex AI Studio, поэтому первый
заход делаем на них.

**Если качество не устроит — переходим на другие модели.** Это ожидаемый и заранее
допущенный исход, а не аварийный случай.

Отсюда требование к коду: **поддержка разных поставщиков закладывается сразу**, с самого
первого захода. Yandex — это первый выбор по умолчанию, а не единственный вариант.
Привязки к Yandex в бизнес-логике быть не должно: смена поставщика обязана сводиться к
изменению настроек, а не к переписыванию кода разбора статей или пополнения словаря.

## Что это значит на практике

- Обращения к модели идут через **собственный интерфейс** (например `LlmClient`), а не
  через классы конкретного поставщика. Бизнес-логика знает только про этот интерфейс.
- Реализации подключаются по настройке: `vocabulary.llm.provider: yandex | openai | ...`.
  Добавление нового поставщика — это новая реализация интерфейса плюс строчка в настройках.
- **Общий знаменатель — интерфейс, совместимый с OpenAI Chat Completions.** Его понимают и
  Yandex AI Studio, и OpenAI, и большинство остальных, включая локальные запуски. Поэтому
  одна реализация поверх Chat Completions закрывает сразу большинство поставщиков, а
  различия (адрес службы, способ входа, имя модели) выносятся в настройки.
- Ничего специфичного для поставщика — в настройках, не в коде: адрес службы, ключ доступа,
  имя модели, ограничения на частоту запросов.
- Формат ответа модели (какие поля мы ждём от разбора слова) описывается **один раз** и не
  зависит от поставщика.

## Настройки Yandex AI Studio

Интерфейс совместим с OpenAI Chat Completions.

| Параметр | Значение |
|---|---|
| Адрес службы | `https://ai.api.cloud.yandex.net/v1`, метод `/chat/completions` |
| Вход | заголовок `Authorization: Bearer $YANDEX_AI_TOKEN` |
| Каталог | `YANDEX_FOLDER_ID` — модель адресуется как `gpt://<folder_id>/<модель>` |
| Переменные окружения | `YANDEX_AI_TOKEN`, `YANDEX_FOLDER_ID`, `YANDEX_AI_BASE_URL` |

Модели для первых опытов: `qwen3.6-35b-a3b/latest` (быстрая, устойчиво отдаёт JSON),
`yandexgpt-5-pro/latest`, `yandexgpt-5.1/latest`. Имена моделей в витрине не совпадают с
их именами в интерфейсе — сверяться с консолью.

Структурированный ответ просить через `response_format: {type: "json_object"}` и разбирать
самим. Режим со схемой JSON в Responses API на Yandex вёл себя неустойчиво.

## Как решать, устроило ли качество

Чтобы «качество не устроило» было проверяемым утверждением, а не ощущением, нужен
**набор для сверки**: несколько десятков слов из исходной базы, разобранных вручную —
часть речи, разделение значений, связь с корнями. На нём прогоняются разные модели и
сравниваются по одним и тем же меркам.

Набор для сверки собираем на этапе 9, до подключения модели к пополнению базы. Без него
сравнивать поставщиков будет не с чем, и решение о смене модели придётся принимать вслепую.

Мерки для сверки:

- доля правильно определённых частей речи;
- доля правильно разделённых значений (главная задача — 72 % статей исходной базы значения
  не разделяют, см. [source-db.md](source-db.md), раздел 5.2);
- доля верных ударений в словоформах;
- доля выдумок в блоке о связи с корнями — самое опасное место, проверять придирчиво.
