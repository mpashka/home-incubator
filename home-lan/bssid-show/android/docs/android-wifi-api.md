# Что можно и чего нельзя с Wi-Fi на современном Android

Родитель: [`index.md`](index.md). **Читать до первой строки кода.**

Собрано, чтобы не потратить день на API, которые выглядят рабочими, компилируются без
предупреждений и молча возвращают `false` или заглушку. Проверять утверждения отсюда стоит на
живом телефоне: поведение различается между версиями и прошивками (у Xiaomi — особенно).

## Функция 1: прочитать текущий BSSID — реализуема

`@tag:bssid-read`

### Как читать

- `WifiManager.getConnectionInfo()` — **устарел с API 31**. Работает, но новый код на нём
  писать не надо.
- Актуальный путь: `ConnectivityManager.registerNetworkCallback()` →
  в `onCapabilitiesChanged` взять `NetworkCapabilities.getTransportInfo()` и привести к
  `WifiInfo` (API 29+). Оттуда `bssid`, `ssid`, `rssi`.

> **Проверено на живом телефоне 07.08.2026** (POCO `2510DPC44G`, HyperOS, Android 16, API 36).
> Совет выше на этом телефоне **неверен**: современный путь отдаёт заглушку, а устаревший —
> настоящий адрес. При выданном `ACCESS_FINE_LOCATION`, включённых службах геолокации
> (`location_mode=3`) и приложении на переднем плане один и тот же вызов дал:
>
> ```
> getTransportInfo()   -> 02:00:00:00:00:00
> getConnectionInfo()  -> d4:da:21:71:10:22
> ```
>
> То же видно и со стороны системы: в `NetworkCapabilities`, которые ConnectivityService
> рассылает приложениям, `TransportInfo` приходит с уже вырезанными SSID и BSSID
> (`SSID: <unknown ssid>, BSSID: 02:00:00:00:00:00`), а `RSSI` и частота — настоящие.
>
> Поэтому приложение спрашивает **оба источника и берёт тот, что дал настоящий адрес**
> (`Wifi.info()`). Устаревший вызов выкидывать нельзя: сегодня он единственный работающий.
> `ACCESS_COARSE_LOCATION` в манифест добавлено рядом с `FINE` — с API 31 их полагается
> запрашивать парой; на исход именно этой проверки оно не повлияло.

### Чем это ограничено

| условие | что будет, если не выполнено |
|---|---|
| разрешение `ACCESS_FINE_LOCATION` | `getBSSID()` вернёт `02:00:00:00:00:00` |
| **службы геолокации включены** в системе | то же самое — мало выдать разрешение |
| приложение на переднем плане (API 29+) | в фоне BSSID не отдаётся без `ACCESS_BACKGROUND_LOCATION` |

Заглушка `02:00:00:00:00:00` — не ошибка и не исключение: система возвращает её молча. Код
обязан отличать её от настоящего адреса и показывать пользователю понятную причину.

На API 33+ появилось `NEARBY_WIFI_DEVICES`. Оно **не заменяет** геолокацию для чтения BSSID,
если объявлено с `usesPermissionFlags="neverForLocation"`. Так что `ACCESS_FINE_LOCATION`
остаётся обязательным.

### Главная сложность — обновление виджета

Виджет живёт в фоне, а в фоне BSSID не отдаётся. Варианты, все с ценой:

| подход | цена |
|---|---|
| `ACCESS_BACKGROUND_LOCATION` | самое неприятное для пользователя разрешение, требует отдельного похода в настройки |
| foreground service с `NetworkCallback` | постоянное уведомление в шторке |
| `updatePeriodMillis` у виджета | минимум 30 минут — для отслеживания переходов бесполезно |
| обновление по нажатию на виджет | ноль фона, но надпись показывает состояние на момент последнего нажатия |

Неявный broadcast `WifiManager.NETWORK_STATE_CHANGED_ACTION` **нельзя** объявить в манифесте
(ограничения неявных broadcast'ов с Android 8) — только регистрация во время работы, то есть
всё равно нужен живой компонент.

Начни с **обновления по нажатию** — это ленивый вариант, не требующий ни фонового разрешения,
ни уведомления. Если окажется мало, поднимай до foreground service.
`ponytail:` начинаем с обновления по нажатию, апгрейд — foreground service, если пользователю
понадобится наблюдать переходы не трогая телефон.

## Функция 2: переключить на нужную точку — полностью НЕ реализуема

`@tag:ap-switch`

> **Функция не делается** (решение пользователя, 07.08.2026). Раздел оставлен как ответ на
> вопрос «а почему бы просто не…»: в коде приложения этого нет и быть не должно.

Главное, что надо принять сразу: **на стоковом Android без root приложение не может перевести
телефон на выбранную точку доступа.** Решение об ассоциации принимает система, и с API 29 у
приложений забрали все рычаги. Задача сводится к тому, чтобы выбрать наименее плохой обходной
путь и честно показать пользователю, что произошло.

### Тупики — сюда не ходить

Всё перечисленное компилируется, но для приложений с `targetSdk` 29+ возвращает `false` или
работает вхолостую:

- `WifiManager.setWifiEnabled()` — no-op, включить/выключить Wi-Fi нельзя;
- `WifiManager.addNetwork()` / `enableNetwork()` / `removeNetwork()` — не действуют на сети,
  которые создало не ваше приложение;
- `WifiManager.disconnect()` / `reconnect()` / `reassociate()` — no-op;
- `WifiConfiguration` целиком, включая поле `BSSID`, — устарел.

Именно эти вызовы предлагает большинство ответов на StackOverflow: они написаны до Android 10.

### Что действительно есть

**`WifiNetworkSpecifier` + `setBssid()`** (API 29+, не устарел) — через
`ConnectivityManager.requestNetwork()`. Единственный способ подключиться к **конкретному
BSSID**. Оговорки, которые делают его не тем, чем кажется:

- система показывает свой диалог выбора — пользователь подтверждает соединение;
- полученная сеть по умолчанию **local-only, без интернета**; телефон не переносит на неё
  маршрут по умолчанию;
- соединение живёт, только пока зарегистрирован ваш `NetworkCallback`; снялись — оно
  исчезло. Чтобы трафик пошёл через неё, нужен `bindProcessToNetwork()`, и это привяжет её
  к вашему процессу, а не ко всему телефону.

То есть «постоянно перевести телефон на кухонную точку» этим не сделать.

**`WifiNetworkSuggestion` + `setBssid()`** (API 29+) — подсказка системе на будущее.
Немедленного переключения не даёт, момент выбирает система. Как рычаг «переключи сейчас»
не годится.

**`Settings.Panel.ACTION_WIFI`** — открыть системную панель Wi-Fi поверх приложения.
Работает всегда, ничего не требует. Пользователь делает одно нажатие сам.

### Практический выход: у нас есть именные сети

Ключ к задаче в том, как настроена домашняя сеть. Кроме общей `m260G` **у каждой точки есть
своя именная сеть** — `m260lG`, `m260bG`, `m260kG` (см. [`home-aps.md`](home-aps.md)).

Поэтому «переключиться на кухонную точку» = «подключиться к сети `m260kG`», а это обычная
смена сети, которую пользователь делает двумя нажатиями. Задача приложения — сократить путь:
нажатие на виджет открывает панель Wi-Fi, где нужная сеть уже видна.

Это и есть тот самый «пнуть Wi-Fi с просьбой», о котором просил пользователь, — реализуемый
надёжно и без экзотических разрешений.

### Если захочется настоящего переключения

| путь | что даёт | цена |
|---|---|---|
| **Shizuku** | выполнять `cmd wifi …` с правами ADB, без root | пользователь поднимает Shizuku после каждой перезагрузки (или по USB, или с root) |
| **root** | `wpa_cli -i wlan0 roam <bssid>` — честный роуминг на конкретный BSSID | нужен root |
| **device owner** | полный контроль над Wi-Fi | только на специально подготовленном устройстве |

`wpa_cli roam` — единственный способ заставить телефон перейти на конкретный BSSID **внутри
той же сети**, то есть по-настоящему решить исходную задачу. Стоит проверить, есть ли root на
Poco F8 / Poco X6, прежде чем городить обходные пути.

## Порядок работы

1. Сделать функцию 1 полностью: чтение BSSID, карта в комнату, виджет, обработка отказа
   в геолокации и заглушки `02:00:00:00:00:00`.
2. Функцию 2 начать с нажатия → `Settings.Panel.ACTION_WIFI`. Это уже полезно.
3. Только потом, если пользователь захочет, — Shizuku или root для настоящего `roam`.

Не начинай со второй функции: велик риск потратить всё время на выяснение того, что уже
написано выше.

## Что проверено на железе

Callback `SCAN_RESULTS_AVAILABLE_ACTION` не гарантирует новые результаты: планшет Lenovo TB376FC
повторил почти один набор из 39 BSSID на трёх точках. Свежесть определяется по монотонному
`ScanResult.timestamp` относительно начала замера, старые строки в свежий скан не попадают.
Проверено на том же планшете в файле `survey-20260808-1836.csv`: первая попытка осталась `cached=1`, повтор дал свежий снимок.

POCO `2510DPC44G`, HyperOS, Android 16 (API 36), 07.08.2026.

| утверждение | итог |
|---|---|
| без `ACCESS_FINE_LOCATION` система молча отдаёт `02:00:00:00:00:00` | **подтвердилось** |
| `getTransportInfo()` — актуальный способ получить BSSID | **опровергнуто**: отдаёт заглушку и с разрешением, см. врезку выше |
| `getConnectionInfo()` устарел, но работает | **подтвердилось**, и сейчас это единственный работающий путь |
| `RSSI` доступен без разрешения на геолокацию | **подтвердилось**: в урезанном `WifiInfo` RSSI и частота настоящие |
| `getScanResults()` тоже урезан, как `getTransportInfo()` | **не подтвердилось**: сканы приходят с настоящими BSSID и уровнями. Урезан именно `TransportInfo`, а не всё подряд |
| `startScan()` требует только разрешений на геолокацию | **опровергнуто**: без `CHANGE_WIFI_STATE` бросает `SecurityException` и роняет приложение, хотя ничего не меняет. Разрешение обычное, диалога не показывает |
| текущая точка всегда есть в результатах скана | **опровергнуто**: сканер обходит каналы, и BSSID, к которому телефон подключён, в конкретный проход попадает не всегда. Для замеров эту строку приходится дописывать из `WifiInfo` отдельно |

Остальное (фоновые ограничения, тупики функции 2) на железе **не проверялось** — только
разобрано по документации.
